## 1. Serenity 的定位

Serenity 是一套**公开资料驱动的产业链瓶颈研究方法论视角**，不是某位真人参与、审核或背书的数字分身。

它的核心路径是：

```text
市场故事
  → 系统变化
  → 必要零部件与技术环节
  → 产业链分层
  → 供应链卡点 / 稀缺层
  → 候选公司
  → 证据分级
  → 市场可能没看清的地方
  → 什么情况说明判断错了
```

Serenity 不从热门股票列表开始，而是先问：

1. 需求或技术系统到底发生了什么变化？
2. 哪个物理、工程或商业约束最难扩张？
3. 哪一层供应商少、验证慢、扩产难或替代成本高？
4. 哪些公司真正控制或贴近这个卡点？
5. 哪些证据能证明客户需求、认证、产能和利润已经落地？
6. 什么反证会让这条判断降级或失效？

研究输出是优先研究顺序、证据链、风险和下一步核验动作，不是收益承诺或确定性买卖指令。

## 2. 产品中的专家能力

### 2.1 专家中心

入口：`#/personas`

Serenity 在专家中心以普通方法论专家显示，主要信息包括：

- 名称：Serenity；简称：链；
- 角色：产业链瓶颈研究；
- 方法标签：供应链卡点、证据分层、逆向核验；
- 能力：研判 · 开放对谈；
- 特殊提示：先制定并封存研究计划。

它不使用真人身份模拟声明，因为这里展示的是方法论资源，不是某位真人的拟人化观点。

### 2.2 专家对谈

Serenity 可以在“专家对谈”中讨论：

- AI、半导体、CPO、先进封装、机器人、电力设备、散热、材料等产业链；
- 行业供需、库存、利用率、资本开支和价格利润周期；
- 一家公司是否控制卡点，还是仅仅受益于热门主题；
- 客户认证、供应商数量、替代路径和扩产周期；
- 研究方法学习和投资 thesis 压力测试。

Serenity 对谈必须提供一个非空研究主题。原因是没有主题就无法形成有边界的研究计划。

### 2.3 大师研判

Serenity 也可以作为个股研判专家使用。与普通大师的单阶段报告不同，Serenity 个股研判执行：

```text
选择股票与 Serenity
  → 获取股票研究上下文
  → 规划阶段：生成 PLAN.md
  → 计划校验与不可变封存
  → 同一 DSH Session 进入研究阶段
  → 生成 REPORT.md
  → 报告校验与不可变封存
  → 同一 Session 继续追问
```

## 3. 数据所有权与安全边界

### 3.1 DSH 是聊天事实源

以下内容只由 DSH Session Persistence 保存：

- 用户消息；
- 助手回答；
- 推理过程；
- 工具调用及结果；
- Turn 状态、队列、取消和审批事件；
- 会话附件。

Hanai 不创建 `messages`、`turns` 或聊天副本表。

### 3.2 Hanai 保存研究业务制品

Hanai SQLite 和业务文件保存：

- 专家、研判和对谈索引；
- opaque `dshSessionId`；
- 专家快照版本；
- 研究计划状态和版本指针；
- 研究计划封存文件、manifest、SHA-256 和大小；
- 个股研判的报告版本和报告封存元数据。

默认路径：

```text
~/.dsh-mode-investment/
├── db/dsh-mode-investment.sqlite
├── judgements/<judgement-id>/
│   ├── workspace/
│   │   ├── AGENTS.md
│   │   ├── RESEARCH_CONTEXT.md
│   │   ├── PLAN.md
│   │   └── REPORT.md
│   ├── plans/0001/
│   │   ├── plan.md
│   │   └── manifest.json
│   └── reports/0001/
│       ├── report.md
│       └── manifest.json
└── expert-chats/<chat-id>/
    ├── workspace/
    │   ├── AGENTS.md
    │   └── PLAN.md
    └── plans/0001/
        ├── plan.md
        └── manifest.json
```

计划正文可以作为研究制品封存，但不替代 DSH 对话历史，也不应把完整对话复制进 SQLite。

### 3.3 研究边界

- 使用公开资料；时效事实需要联网核验；
- 公司、客户、订单、产能、财务和价格不能凭记忆编造；
- 社交媒体和 KOL 内容只能作为线索；
- 研究输出不构成投资建议；
- 不提供操纵市场、欺骗、规避监管、协调交易或确定性收益方案。

## 4. Serenity 研究方法工作流

### 第一步：界定范围

先明确：

- 市场：A 股、港股、美股或其他市场；
- 主题：AI 基建、半导体、CPO、机器人、电力、材料、设备等；
- 时间窗口：默认关注未来 3—12 个月，除非用户另有要求；
- 研究目标：主题扫描、单家公司挑战、候选比较或方法学习。

### 第二步：把叙事翻译成系统变化

不要停留在“某主题很热”。要写出：

```text
需求波动 → 系统压力 → 技术/工程变化 → 首先变紧的约束
```

例子：

- AI 集群扩大 → 带宽、延迟和功耗压力上升 → 光互连、交换、封装升级 → 激光器、DSP、测试、封装材料可能变紧；
- AI 服务器密度提升 → 供电、散热和稳定性压力上升 → 电源转换、变压器、开关设备、液冷升级 → 认证设备和关键零部件可能成为卡点；
- 人形机器人渗透 → 执行器和感知密度提升 → 减速器、电机、编码器、触觉和电池要求提高 → 良率、精度和供应商验证周期可能成为约束。

### 第三步：拆产业链

建议至少检查以下层级：

1. 终端需求与资本开支来源；
2. 系统集成商与 OEM；
3. 模块和子系统；
4. 芯片、器件和关键零部件；
5. 工艺、封装和测试；
6. 设备、计量与检测；
7. 材料、耗材和特种投入；
8. 电力、厂房、网络和其他物理基础设施。

不同层级的经济学不同，不要把计算芯片、EDA、存储、设备、材料、封测、光模块、PCB 和电源简单合并成一个“AI 概念”桶。

### 第四步：寻找稀缺层

当以下信号同时出现时，才把某一层列为高优先级卡点候选：

- 客户扩张离不开它；
- 有效供应商数量少；
- 客户认证或导入周期长；
- 产能扩张需要专用设备、许可、工艺经验或高纯度材料；
- 订单、预付款、产能锁定、长协或交付周期体现客户紧迫性；
- 价格和毛利率能够反映真实稀缺；
- 市场仍按旧业务类别理解公司，没有充分识别其新位置。

先排层级，再排公司。不能因为一家公司股价上涨，就反推它掌握稀缺层。

### 第五步：建立候选池

宽主题扫描时，优先建立跨层级候选池，再筛选 3—7 个优先研究对象。候选应覆盖：

- 明显龙头；
- 上游设备、材料和耗材；
- 工艺和封装；
- 测试和计量；
- 电源、散热、PCB、CCL、光链路等相邻环节；
- 热门但证据较弱的公司，用于明确降级。

每家公司都要标注其属于：

- 控制稀缺层；
- 供应稀缺层；
- 受益于需求但控制力有限；
- 有主题暴露但定价权弱；
- 只有故事、缺少硬证据。

### 第六步：按证据等级核验

**强证据**：

- 交易所文件、年报、半年报、季报、临时公告；
- 公司正式公告、投资者关系材料和业绩会；
- 官方客户合同、订单、中标、产能预约或预付款；
- 环评、能评、项目备案和监管文件；
- 专利、标准、技术论文和认证文件。

**中等证据**：

- 可靠财经媒体和行业媒体；
- 行业协会资料；
- 公司产品页；
- 假设透明的专业研究；
- 上下游公司的公开披露交叉验证。

**弱证据**：

- KOL 帖子、论坛讨论、截图、匿名渠道和单纯价格异动。

对每一个高优先级公司至少回答：

1. 它具体卡住哪一层？
2. 它在产业链中的位置是什么？
3. 至少两条证据是什么？
4. 证据强度是 Strong、Medium、Weak 还是 Needs checking？
5. 还缺哪一条关键证明？
6. 什么情况会让优先级下降？

### 第七步：输出判断和反证

输出顺序建议为：

1. 先给产业链层级排序；
2. 再给公司优先研究排序；
3. 解释每家公司卡住的环节和证据；
4. 点名一个热门但应降级的方向；
5. 给出最大风险和反方理由；
6. 给出下一步具体检查项。

## 5. 研究计划 `PLAN.md` 设计

### 5.1 计划的作用

`PLAN.md` 是正式研究开始前的范围和证据路线快照。它不是报告摘要，也不是聊天记录；它的作用是让研究先回答“准备怎么证明”，再回答“最后结论是什么”。

### 5.2 最低内容要求

当前 Host 会校验：

- 文件存在；
- 至少包含一个一级标题；
- 正文至少 120 个字符；
- 可通过封存 manifest 和 SHA-256 完整性检查。

Serenity 计划应实际包含以下内容：

```markdown
# 研究计划标题

## 1. 研究范围与问题
- 市场、主题、标的、时间窗口

## 2. 系统变化
- 需求为什么变化
- 哪个旧设计或旧约束开始承压

## 3. 产业链分层
- 下游需求
- 系统与模块
- 芯片/器件
- 工艺/封装/测试
- 设备/材料/基础设施

## 4. 供应链卡点假设
- 哪一层最难扩张或替代
- 为什么客户可能绕不开
- 当前证据和证据缺口

## 5. 候选公司与筛选顺序
- 控制卡点
- 供应卡点
- 主题受益但控制力有限

## 6. 证据路线
- 要查的公告、财报、客户认证、订单、产能和财务指标
- 来源优先级与交叉验证方式

## 7. 市场可能没看清的地方
- 旧分类、供应链位置或利润归属的认知偏差

## 8. 反方理由与失效条件
- 替代路线
- 竞争者扩产
- 需求走弱
- 融资、治理、政策和估值风险

## 9. 下一步先查什么
- 具体文件、指标、公告或事件
```

### 5.3 计划封存规则

计划封存采用与报告相同的安全思路：

1. Agent 在工作区写 `PLAN.md`；
2. Host 校验内容；
3. 先写 staging 目录；
4. 原子 rename 到 `plans/0001/`；
5. 写入 manifest；
6. 生成 SHA-256 和字节数；
7. 在 SQLite `research_plans` 中记录 owner、Session、专家版本、路径和指纹；
8. 使用同一个 DSH Session 进入下一阶段。

当前计划 owner 有两类：

- `judgement`：个股研判计划；
- `expert-chat`：开放对谈计划。

普通追问不会修改已封存计划。需要重新规划时，应明确创建新版本或新任务，不能静默覆盖旧制品。

## 6. 两类入口的具体使用方法

### 6.1 从专家中心开始

1. 打开 `http://127.0.0.1:3090/#/personas`；
2. 找到 Serenity 卡片；
3. 查看“产业链瓶颈研究”和方法标签；
4. 进入“专家对谈”或“大师研判”入口。

专家中心是能力说明页，不直接执行任务，也不应因为展示专家卡片而创建 Session。

### 6.2 Serenity 专家对谈

推荐提问：

```text
用 Serenity 的方式研究 A 股 AI 服务器电源链。
先拆产业链，再判断最可能先变紧的层级，最后给出优先研究公司、证据路径、反方理由和失效条件。
```

```text
用 Serenity 挑战“这家公司是 CPO 核心供应商”的说法。
它到底卡在哪一层？客户为什么可能绕不开？哪些证据还缺失？什么情况说明这个判断错了？
```

产品流程：

1. 选择 Serenity；
2. 填写非空开场主题；
3. 创建独立对谈业务记录、专家快照和 DSH Session；
4. 第一轮只制定并写入 `PLAN.md`；
5. Host 校验、封存计划并入库；
6. 同一 Session 自动进入研究阶段；
7. 后续在聊天时间线中继续讨论；
8. 计划完成后可从详情页查看“研究计划”。

开放对谈不生成 `REPORT.md`，但计划作为独立研究制品保存。

### 6.3 Serenity 个股研判

推荐提问：

```text
用 Serenity 研究这家公司在 AI 服务器产业链中的真实位置。
优先判断卡点、客户认证、产能扩张、收入结构和替代路线，不给收益承诺。
```

产品流程：

1. 在“大师研判”选择股票；
2. 选择 Serenity；
3. 创建后状态进入“制定研究计划”；
4. 第一轮生成 `PLAN.md`；
5. Host 校验并封存计划；
6. 自动进入“研判进行中”；
7. 第二阶段根据计划检索公开资料并写 `REPORT.md`；
8. Host 校验、封存报告并建立版本；
9. 在详情页查看报告、研判过程、研究计划或继续对话。

## 7. 状态与故障处理

### 7.1 主要状态

- `planning`：计划尚未通过校验或尚未入库；
- `generating`：计划已封存，研究阶段已排队或执行；
- `verifying`：报告正在校验和封存；
- `repairing`：报告校验失败，正在执行唯一一次报告修复；
- `ready`：研判报告已封存，可继续对话；
- `failed`：计划或报告阶段失败，保留错误信息供删除或重新创建。

计划本身另有业务状态：

- `none`：没有计划；
- `planning`：正在生成计划；
- `ready`：计划已封存；
- `failed`：计划生成或校验失败。

### 7.2 自动修复

计划校验失败时，当前实现允许一次自动修复：

1. Host 保存错误码和错误信息；
2. 保持任务处于计划阶段；
3. 向同一 Session 发送计划修复 prompt；
4. 再次收到 Turn 结束事件后重新校验；
5. 再失败则标记失败，不启动正式研究。

报告阶段沿用既有报告修复逻辑。

### 7.3 重启与幂等

Host 启动时会检查：

- 计划阶段是否仍有 DSH Session；
- 是否已经存在封存计划；
- 计划文件、manifest、SHA-256 和业务索引是否一致；
- 是否可以继续发送研究阶段 prompt。

同一计划版本重复封存时，只接受内容、路径、专家版本和 Session 信息完全一致的既有记录；发现不一致应显式失败，不能静默覆盖。

## 9. 优化路线

以下项目是建议方向，不应当写成当前已实现能力。

### P0：可靠性与一致性

1. **补齐旧数据库迁移矩阵**
   - 为空库、v1、v2、已有旧版 `research_plans` 表和半迁移库增加专门测试；
   - 将 migration DDL、数据回填和 migration marker 变成明确的顺序化步骤；
   - 任何失败都回滚并保留清晰错误。

2. **增加计划事件水印**
   - 在计划 manifest 中记录计划阶段的 Session event seq 或 Turn 标识；
   - 防止旧 `PLAN.md`、重复 `turn/end` 或跨重启事件误被当作当前计划；
   - 计划封存时校验 owner、Session、Turn 和文件内容一致。

3. **修复历史研究渲染测试的子进程调用**
   - 将测试中的 `spawnSync(TSX, ...)` 改为稳定的 `node --import tsx` 调用或统一 runner；
   - 让完整 `pnpm run check` 能够真实反映仓库健康状态。

### P1：计划质量和用户可见性

1. **从“长度校验”升级为“章节校验”**
   - 强制检查系统变化、产业链层级、稀缺层、证据路线、反证、失效条件和下一步；
   - 缺少关键章节时给出结构化错误，而不是只报告字符数不足。

2. **规划阶段即可查看计划草稿状态**
   - 当前详情页重点展示已封存计划；可增加只读规划状态、计划生成进度和封存时间；
   - 明确区分“草稿未封存”和“正式计划已入库”。

3. **展示计划元数据**
   - 显示计划版本、封存时间、大小、SHA-256、专家快照和 DSH Session 关联；
   - 增加“计划与报告的研究问题是否一致”的人工检查提示。

4. **明确重规划策略**
   - 规定报告修订是否重建计划；
   - 若新证据改变系统变化或稀缺层判断，创建 `PLAN.md` v2，而不是覆盖 v1；
   - 报告 manifest 记录使用的计划版本。

### P1：研究结构化

1. **Markdown + 结构化计划 JSON**
   - `PLAN.md` 用于人类阅读；
   - 同时保存 JSON 结构：scope、systemChange、layers、scarceLayer、candidates、evidenceChecks、falsifiers、nextChecks；
   - 便于后续生成任务图、监控规则和计划差异。

2. **从计划生成可见研究任务图**
   - 将证据路线拆成“公司定位、客户验证、产能、财务、估值、替代路线、反方审计”等任务；
   - 展示每个任务的状态、来源覆盖和失败原因；
   - 让用户看到研究工作，而不是内部 Agent 调试细节。

3. **证据与 Claim 绑定**
   - 每个核心判断绑定来源等级、来源日期、原文定位和当前状态；
   - 记录事实、推断、假设和未知项的区分；
   - 当来源失效或过期时提示重新核验。

### P2：研究效率与持续跟踪

1. **跨层候选池模板**
   - 为 AI 半导体、AI 电力、机器人、CPO、先进封装等主题提供层级模板；
   - 默认覆盖至少 20 个候选，再筛到 3—7 个优先研究对象。

2. **同主题多专家对照**
   - Serenity 负责卡点与供应链证据；
   - 巴菲特/芒格负责商业质量、估值和永久损失；
   - 混江龙负责题材周期和市场交易结构；
   - 通过冻结事实包比较分歧，而不是把不同角色简单平均。

3. **计划差异与报告回溯**
   - 计划 v1 → v2 显示新增、删除和降级的研究问题；
   - 报告每个结论可回溯到计划中的问题和对应证据；
   - 允许用户看到“哪些假设改变了结论”。

4. **监控收件箱**
   - 将计划中的“下一步先查什么”和“失效条件”转成可选监控规则；
   - 监控公告、财报、订单、产能、客户认证、库存和估值变化；
   - 只有用户确认后才重开研究或生成报告修订任务。

5. **本地 scorecard 集成**
   - 将上游 `serenity_scorecard.py` 接入研究计划或候选表；
   - 固定评分输入、版本和哈希；
   - 评分只作为排序辅助，不把分数包装成概率或收益预测。

## 10. 推荐的日常操作顺序

```text
1. 从专家中心确认 Serenity 的方法边界
2. 在专家对谈中先讨论主题和系统变化
3. 查看已入库 PLAN.md，确认卡点和证据路线
4. 再对具体公司发起大师研判
5. 对照 REPORT.md 与 PLAN.md 是否回答同一问题
6. 从报告的反证与待验证项建立后续跟踪
7. 只有新事实改变核心假设时才重新规划或修订
```

建议始终保留以下三类记录：

- **事实**：来源、日期、数据口径；
- **推断**：从事实推导出的产业链判断；
- **假设**：仍需要验证、可能被反证推翻的部分。

这三类内容分开，Serenity 才能发挥“先找卡点、再找公司、最后找反证”的价值。
